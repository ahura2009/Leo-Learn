# احراز هویت Leo Learn

این سند قرارداد بین فرانت‌اند و بک‌اند احراز هویت است. شمارهٔ موبایل جایگزین
ایمیل شده و **هیچ OTP نمایشی در مرورگر ساخته نمی‌شود**؛ کد فقط در سرور تولید
می‌شود، هش‌شده ذخیره می‌شود و فقط با پیامک به شمارهٔ کاربر می‌رود.

## وضعیت فعلی

| بخش | وضعیت |
|---|---|
| UI ورود / ثبت‌نام / تأیید کد / بازیابی رمز | پیاده‌سازی شده |
| کلاینت auth و نشست کوکی HttpOnly | پیاده‌سازی شده |
| گیت مسیرها: بدون ورود → sign-in، تازه وارد → onboarding | پیاده‌سازی شده |
| سرور auth نمونه (`server/auth`) با scrypt، OTP هش‌شده، Rate limit | پیاده‌سازی شده و تست دارد |
| سرویس پیامکی واقعی | **نیازمندی فنی** — کلید Kavenegar (یا webhook) هنوز تنظیم نشده |
| ذخیره‌سازی تولیدی (Postgres/Redis) | **نیازمندی فنی** — نمونه از SQLite استفاده می‌کند |
| استقرار روی دامنهٔ هم‌سایت با HTTPS | **نیازمندی فنی** — GitHub Pages استاتیک نمی‌تواند سرور auth را اجرا کند |
| تغییر شماره، حذف حساب، ورود دوعاملی | خارج از دامنهٔ این مرحله |

> اگر `NEXT_PUBLIC_AUTH_API_URL` تنظیم نشده باشد، UI صادقانه می‌گوید سرویس
> متصل نیست و هیچ جریان ساختگی اجرا نمی‌کند.

## مسیرها

| مسیر | کار |
|---|---|
| `/App/sign-in` | ورود با موبایل + رمز؛ نمایش/مخفی‌کردن رمز؛ لینک فراموشی رمز |
| `/App/sign-up` | نام، موبایل، رمز، تکرار رمز، پذیرش قوانین → ارسال OTP |
| `/App/verify` | صفحهٔ کد ۶ رقمی، شمارش معکوس ارسال دوباره، تغییر شماره |
| `/App/forgot-password` | درخواست کد بازیابی |
| `/App/reset-password` | کد + رمز تازه + تکرار رمز |
| `/App/onboarding` | فقط بعد از ورود؛ سطح و هدف (نام در ثبت‌نام گرفته شده) |
| `/App` و بقیهٔ صفحات اپ | فقط با نشست معتبر و onboarding تمام‌شده |

جریان بعد از موفقیت:

- کاربر قدیمی (onboarding تمام‌شده) → `/App`
- کاربر تازه → `/App/onboarding`
- بعد از بازیابی رمز → همان مقصد بر اساس همین قاعده

## قوانین اعتبارسنجی

- موبایل: اعتبارسنجی با `libphonenumber-js` و فرادادهٔ کشورها؛ نتیجه در سرور
  هم دوباره به E.164 یکسان می‌شود. پیش‌شمارهٔ کشور قابل انتخاب و جست‌وجو است،
  تشخیص شمارهٔ کامل با `+` و پذیرش ارقام فارسی/عربی.
- رمز: حداقل ۸ و حداکثر ۷۲ کاراکتر، حداقل یک حرف و یک رقم، و هم‌سان با
  شمارهٔ موبایل نباشد.
- کد: ۶ رقم، اعتبار ۵ دقیقه، حداکثر ۵ تلاش، ارسال دوباره با فاصلهٔ ۶۰ ثانیه.
- نام: ۲ تا ۲۴ حرف.

## قرارداد API

پایه: `NEXT_PUBLIC_AUTH_API_URL` (مثلاً `https://app.leolearn.ir/v1`) یا در
توسعه `/v1` که Next به سرور محلی proxy می‌کند. همهٔ درخواست‌ها JSON و با
`credentials: include` هستند.

| متد و مسیر | بدنه | پاسخ |
|---|---|---|
| `POST /auth/sign-up/start` | `{name, phone, password}` | `201 {challenge}` |
| `POST /auth/sign-up/verify` | `{challengeId, code}` | `200 {user}` + کوکی نشست |
| `POST /auth/sign-in` | `{phone, password}` | `200 {user}` + کوکی نشست |
| `GET /auth/session` | — | `200 {user}` یا `401` |
| `POST /auth/sign-out` | — | `204` |
| `POST /auth/challenges/resend` | `{challengeId}` | `200 {challenge}` |
| `POST /auth/password/forgot` | `{phone}` | `200 {challenge}` (همیشه) |
| `POST /auth/password/reset` | `{challengeId, code, password}` | `200 {user}` + کوکی |
| `PATCH /auth/profile` | `{name?, level?, goal?}` | `200 {user}` |
| `GET /health` | — | `200 {ok}` |

`challenge`:

```json
{
  "challengeId": "uuid",
  "purpose": "signup | reset",
  "phone": "+989121234567",
  "expiresAt": "2026-11-24T09:24:58.588Z",
  "resendAfterSeconds": 60,
  "codeLength": 6
}
```

`user`:

```json
{
  "id": "uuid",
  "phone": "+989121234567",
  "name": "سارا",
  "level": "A2",
  "goal": "travel",
  "createdAt": "2026-11-24T09:19:58.588Z",
  "onboardedAt": "2026-11-24T09:26:31.000Z"
}
```

### خطاها

بدنه: `{"error": {"code": "...", "message": "...", "attemptsLeft"?, "retryAfterSeconds"?}}`

| code | معنی | پیام UI |
|---|---|---|
| `PHONE_INVALID` | شماره معتبر نیست | «شمارهٔ موبایل معتبر نیست…» |
| `PHONE_TAKEN` | شماره قبلاً ثبت‌نام کرده | «وارد شو یا رمزت را بازیابی کن» |
| `PASSWORD_INVALID` | رمز قوانین را نمی‌گذراند | راهنمای رمز |
| `CODE_INVALID` | کد اشتباه + `attemptsLeft` | «کد درست نیست؛ n تلاش…» |
| `CODE_EXPIRED` | کد منقضی شده | «کد تازه بگیر» |
| `TOO_MANY_ATTEMPTS` | سقف تلاش کد | «کد تازه بگیر» |
| `RATE_LIMITED` | ارسال دوباره زودهنگام + `retryAfterSeconds` | شمارش معکوس |
| `CHALLENGE_NOT_FOUND` | چالش نیست/مصرف شده | شروع دوباره |
| `INVALID_CREDENTIALS` | شماره یا رمز اشتباه (عمومی) | «شماره یا رمز درست نیست» |
| `ACCOUNT_LOCKED` | ۶ تلاش ناموفق در ۱۵ دقیقه | «موقتاً قفل شده» |
| `NOT_CONFIGURED` | سمت کلاینت، آدرس API تنظیم نشده | بنر تنظیم‌نشده |
| `NETWORK` / `SERVER_ERROR` | خطای اتصال/سرور | تلاش دوباره |

صفحهٔ فراموشی رمز برای شمارهٔ ناموجود هم پاسخ یکسان `200` با چالش ساختگی
می‌دهد تا امکان شمارش حساب‌ها از راه این مسیر کم شود.

## نشست

- کوکی `leo_auth`، `HttpOnly; SameSite=Lax; Path=/` و در production `Secure`.
- توکن تصادفی ۳۲ بایتی؛ در دیتابیس فقط HMAC-SHA256 آن ذخیره می‌شود.
- عمر ۳۰ روزه. تغییر رمز همهٔ نشست‌های قبلی همان کاربر را باطل می‌کند.
- هیچ توکنی در localStorage نیست و JS آن را نمی‌خواند.
- برای تست/موبایل، سرور `Authorization: Bearer <token>` را هم می‌پذیرد.

## اجرای محلی

```bash
# ترمینال ۱ — بک‌اند auth (SQLite + پیامک ترمینال در توسعه)
AUTH_SESSION_SECRET="local-development-secret-32-characters"
AUTH_SMS_PROVIDER=console
npm run auth:server

# ترمینال ۲ — فرانت‌اند
npm run dev
```

Next درخواست‌های `/v1/*` را در توسعه به `http://127.0.0.1:8787` هدایت می‌کند
(`next.config.ts` → `rewrites`)، پس کوکی هم‌سایت می‌ماند و CORS لازم نیست.

با provider `console` کد **فقط در لاگ سرور** چاپ می‌شود و هرگز در پاسخ HTTP
یا UI نمی‌آید. این provider در `NODE_ENV=production` عمداً خطا می‌دهد.

تست‌ها:

```bash
npm test          # قوانین موبایل/رمز + منطق داشبورد
npm run test:server
```

## متغیرهای محیطی

فهرست کامل در `.env.example`. مهم‌ترین‌ها:

| متغیر | کار |
|---|---|
| `NEXT_PUBLIC_AUTH_API_URL` | آدرس API برای مرورگر (در build درج می‌شود) |
| `AUTH_SESSION_SECRET` | امضای توکن نشست/OTP — production ≥ ۳۲ کاراکتر |
| `AUTH_SMS_PROVIDER` | `mediana` \| `kavenegar` \| `webhook` \| `console` (فقط توسعه) |
| `MEDIANA_API_KEY` / `MEDIANA_PATTERN_CODE` | ارسال OTP واقعی با مدیانا |
| `KAVENEGAR_API_KEY` / `KAVENEGAR_OTP_TEMPLATE` | ارسال OTP واقعی |
| `AUTH_ALLOWED_ORIGINS` | مبدأهای مجاز CORS |
| `AUTH_DB_PATH` | مسیر SQLite برای نمونه |

## نیازمندی‌های استقرار واقعی

1. **دامنهٔ هم‌سایت + HTTPS.** کوکی `SameSite=Lax` و `Secure` فقط وقتی مطمئن
   کار می‌کند که فرانت و API زیر یک سایت باشند (مثلاً `app.leolearn.ir` و
   `api.leolearn.ir`، یا API پشت همان دامنه با `/v1`). استقرار روی
   `github.io` بدون دامنهٔ اختصاصی نمی‌تواند نشست کوکی را بپذیرد.
2. **هاست سروری برای API.** GitHub Pages استاتیک است و نمی‌تواند
   `server/auth` را اجرا کند. فرانت را روی Vercel/سرور Node و auth را روی
   همان دامنه یا reverse proxy منتشر کنید.
3. **سرویس پیامکی.** حساب Kavenegar (یا webhook به سرویس دیگر) با الگوی
   تأیید و اعتبار کافی. بدون آن، ثبت‌نام در production کار نمی‌کند و این
   عمداً به‌جای OTP نمایشی، خطای صریح می‌دهد.
4. **ذخیره‌سازی تولیدی.** جایگزینی SQLite با Postgres (+ Redis برای Rate
   limit و قفل) پیش از ترافیک واقعی؛ در غیر این صورت سرویس تک‌نمونه است.
5. **پایش و پشتیبان‌گیری.** لاگ بدون کد/رمز، هشدار نرخ خطای پیامک، بکاپ
   دیتابیس.

## تصمیم‌های امنیتی پیاده‌شده

- رمز با `scrypt` (N=16384) و نمک تصادفی؛ مقایسهٔ زمان‌ثابت.
- کد با HMAC-SHA256 بر پایهٔ شناسهٔ چالش + راز سرور ذخیره می‌شود.
- سقف تلاش برای کد، قفل موقت ورود بعد از ۶ خطا، سقف ارسال پیامک.
- پاسخ یکسان برای شمارهٔ ناموجود در فراموشی رمز و ورود ناموفق.
- بررسی Origin برای درخواست‌های cross-origin، CORS با allowlist دقیق.
- سقف حجم بدنه (۱۶KB)، سقف نرخ درخواست هر IP، هدرهای `nosniff` و
  `no-referrer`، `Cache-Control: no-store`.
- ورودی سمت سرور دوباره اعتبارسنجی می‌شود؛ قوانین کلاینت فقط بازخورد سریع است.

## خارج از این مرحله

- ارسال ایمیل/بازیابی با ایمیل
- تغییر شمارهٔ موبایل پس از ثبت‌نام
- حذف حساب و دانلود داده
- ورود بدون رمز (magic link/OTP-only)
- انتقال پیشرفت درس‌ها به سرور (فعلاً در همان مرورگر و جدا برای هر حساب
  در `localStorage` نگه داشته می‌شود)
